# ゲーム対戦AIで強化学習に入門した記録

対戦ゲーム（不完全情報・3体選出のターン制バトル）のAIを約2週間で開発した過程の記録。
ヒューリスティクスAI → 模倣学習 → PPO → Self-Play と段階的に進め、得られた知見をRL一般に使える形で整理した。

---

## 開発タイムライン

```
Day 1-2   ダメージ計算・1v1シミュレーション（自前エンジン）
Day 3     自前エンジン破棄 → 既存OSSエンジンに移行
Day 3-4   ヒューリスティクスAI構築
Day 5-6   リプレイ収集(1,340件) → 模倣学習
Day 7-8   PPO訓練11世代
Day 9     Self-Play挑戦 → policy forgetting で中断
Day 10-12 メタ分析 → ドメイン理論の定式化
Day 13-14 対戦相手プール拡大(11→32) + 観測空間再設計
```

### 勝率の推移

| フェーズ | 勝率 | 備考 |
|---------|------|------|
| ヒューリスティクスのみ | 49% | 32チームプール |
| + バグ修正5件 | 62% | |
| + ドメイン理論で判断ロジック統一 | 63% | |
| + 状態異常対応 | 71% | 手動チューニングの上限付近 |
| 選出RL (2,000step) | 90% | 選出だけで+26pt |
| バトルRL 最終世代 (24,000step) | 100% | 7チーム固定相手 |

## 1. 環境構築で学んだこと

### 自前エンジンと既存エンジン

自前のバトルエンジンを約1,300行書いた後、OSSで既にルール実装済みの完全なエンジン（約21,000行）が存在すると分かり、全て破棄した。

ゲームAIの場合、エンジンの正確性がRL訓練の信頼性に直結する。自前実装のバグは「間違ったルールで学習する」ことを意味し、実戦で使えないモデルになる。

### 実行速度

WebSocket経由だと1ゲーム15秒、サブプロセス直接通信に変えると1秒。RLの訓練には数万〜数十万エピソードが必要なので、この差は訓練の実現可能性そのものに影響する。環境の速度最適化はアルゴリズム改善より優先度が高い。

### 外部プロセスとの連携

外部エンジンのI/O仕様を「たぶんこういう形式だろう」と想像してコードを書いた結果、11個のバグが発生。全て「エンジンは正しく動いているが、AIがプロトコルを正しく読めていない」問題だった。

対策として以下の手順を確立した：
1. 実I/Oを1エピソード分、生データで保存する
2. 全フィールドを文書化する（存在するもの・しないもの両方）
3. 自分のデータモデルとの対応表を作る
4. 足りない情報と補完手段を特定する
5. テストデータは実データから生成する（手書きしない）

## 2. ヒューリスティクスを先に作る

RLに進む前にルールベースのAIを作った。以下の理由から、この順番は正解だった。

- **対戦相手になる**。ランダムAIでは学習信号が弱すぎる
- **ベースラインになる**。RLの改善幅を正確に測定できる
- **ドメイン知識が整理される**。観測空間や報酬設計のヒントが得られる
- **デバッグに使える**。RLが変な行動をしたとき比較で原因を特定できる

ヒューリスティクスだけで71%に到達し、その過程で「行動回数の収支」というドメイン固有の評価軸を発見した。全ての行動（攻撃・バフ・回復・交代・状態異常）を「行動回数の増減」で統一的に評価する考え方で、110行の分岐ロジックが70行のスコア計算にまとまった。

ドメイン知識を理論として定式化できると、コードの簡潔さと判断精度の両方が改善される。

## 3. 模倣学習の天井

1,340件のリプレイから(状態, 行動)ペアを抽出し、教師あり学習を行った。

| タスク | 精度 |
|--------|------|
| 攻撃 or 交代 の2値分類 | 82%（ベースライン68%） |
| どの技を使うか | 45%（天井） |
| 誰に交代するか | 97% |

技選択が45%で止まるのは不完全情報ゲームの構造的な制約。同じ盤面でも相手の隠し情報次第で最適解が変わり、混合戦略が最適な局面では「正解」を1つに定められない。

一方、交代先の選択は97%と高精度で、タイプ相性のような決定的要素がある部分問題には模倣学習が十分に有効だと分かった。

模倣学習は初期方策の獲得手段としては有用だが、不完全情報ゲームの最終解にはならない。

## 4. PPO訓練で遭遇した問題

### 4-1. 学習が進まない（clip_fraction = 0）

デフォルトの学習率(lr=3e-4)が小さすぎて方策が更新されなかった。lr=1e-3に上げたら学習が開始。PPOのデフォルトハイパラは連続制御タスク向けのことが多い。離散行動空間のゲームでは、まず学習率を上げて動作確認するのがよい。

### 4-2. 過学習によるエントロピー崩壊（75% → 20%）

対戦相手が固定1チームだったため、特定の相手専用の方策に過適合。行動の多様性がゼロに近づき、汎化能力を喪失した。対戦相手をプールからランダム選択に変更して解決。

固定相手で100%になっても「相手の癖を暗記した」だけであり、汎化とは異なる。

### 4-3. 違法手の探索

残り回数ゼロの技や、瀕死の味方への交代を試みる問題。MaskablePPO（sb3-contrib）で違法手をマスクしたところ、勝率が+11pt。違法手への罰則報酬より、選択肢から除外する方が効率的。

### 4-4. 学習率の減衰

6,000ステップ付近で再びエントロピー崩壊が発生。学習率をlinear decay（5e-4 → 5e-5）させることで安定して78%まで到達。初期は大きく探索し、後半は小さく収束させる設計が必要。

### 世代別の推移

```
Gen 1  (defaults)           →   0%   学習率不足
Gen 2  (lr=1e-3)            →  75% → 20%   過学習崩壊
Gen 3  (MaskablePPO)        →  60%   マスクで安定
Gen 4  (weight transfer)    →  71%   前世代の知識を継承
Gen 8  (lr decay)           →  78%   崩壊防止
Gen 11 (selection RL併用)   → 100%   選出最適化が決定打
```

## 5. 観測空間の設計

### 設計原則

「人間がプレイ中に見ている情報と同等の情報をエージェントに渡す」を方針とした。

| 版 | 次元数 | 追加した情報 | まだ欠けていた情報 |
|----|--------|-------------|------------------|
| v1 | 76 | 自キャラの基礎値・技威力 | 相手の技、バフ、フィールド状態 |
| v2 | 101 | 相手の基本情報 | 控えの詳細、設置物 |
| v3 | 186 | 控え全情報・バフ・フィールド | 装備、判明済み技、行動順 |
| v4 | 278 | 装備・判明技・速度推測 | — |

設計上の要点：
- **カテゴリ変数はone-hot**にする（属性18種、フィールド状態4種など）
- **連続値は[0, 1]に正規化**する（HP、攻撃力など）
- **不明情報はゼロベクトル**で表現するが、「欠損」と「値がゼロ」の区別に注意
- **推測材料を含める**。行動順の履歴5ターン分を入れることで、相手の速度を間接推定可能にした

### サブタスクの分離

RL基盤ライブラリ（SB3）が固定次元の観測・行動空間を前提とするため、性質の異なるサブタスクを2つの独立モデルに分けた。

| Agent | 観測 | 行動 | 性質 |
|-------|------|------|------|
| 選出Agent | 360dim | Discrete(20) | 1ステップの contextual bandit |
| バトルAgent | 278dim | Discrete(9) | 多ステップのMDP |

行動空間の構造が異なるサブタスクは、1モデルに詰め込むより分離した方が扱いやすい。

## 6. Self-Playで起きたこと

### Policy Forgetting

Self-Playで方策を更新すると、旧方策で学んだ知識が消える。ヒューリスティクス相手に86%を達成した方策は「ヒューリスティクスの癖を突く」ことに特化しており、未知の戦略に対して脆弱だった。

### 分布ミスマッチ

選出モデルを改善したところ、バトルモデルが壊れた。バトルモデルは旧選出パターン（毎回同じ3体）で訓練されており、新選出で未経験のキャラが出ると行動がランダムに退化する。

対策として選出モデルを固定し、バトルモデルをゼロから再訓練。新しい選出パターンを最初から経験させることで100%に到達した。

マルチモデル構成では、上流コンポーネントの変更が下流の前提を崩す。パイプラインの途中を差し替えたら、下流の再訓練が必要になる。

## 7. 横断的な知見

### RL の前にやることがある

```
ランダム → ヒューリスティクス → 模倣学習 → RL
```

ヒューリスティクスで十分な勝率を確保してからRLに進むことで、対戦相手の質・ベースラインの明確さ・ドメイン知識の蓄積が全て改善される。

### 報酬設計はシンプルから始める

| イベント | 報酬 |
|---------|------|
| 勝利 / 敗北 | ±1.0 |
| 相手を倒す / 味方が倒される | ±0.3 |
| HPの変化 | ±0.1 |

倒した/倒された報酬がないと「倒すこと」と「勝利」の因果関係の学習が遅い。HP差分報酬は毎ターンのフィードバックとして学習を安定させる。

### ログ解析

バトルログの解析から11個のバグを発見した。RLの行動がおかしいとき、問題はモデルではなく環境（観測の欠落・状態管理のバグ）にあることが多い。

### テスト

RL環境のバグは訓練結果を丸ごと無駄にする。ダメージ計算・属性相性・特殊効果・環境のstep/reset・観測空間の構築に対して253テストを書いたことで、安心してリファクタリングを繰り返せた。

## 8. 技術スタック

| 用途 | ツール |
|------|--------|
| RL環境定義 | Gymnasium |
| PPO実装 | Stable-Baselines3 + sb3-contrib (MaskablePPO) |
| 言語 | Python 3.12 |
| テスト | pytest |

### 始める場合の推奨順序

1. Gymnasium公式チュートリアルで CartPole / LunarLander を動かす
2. SB3のGetting StartedでPPOを最小構成で訓練する
3. 自分の問題をGymnasiumのenvとして定義する（observation_space, action_space, step, reset）
4. ヒューリスティクスのベースラインを先に作る
5. MaskablePPOで合法手マスクを使う（ゲームの場合）
6. TensorBoardで学習曲線を監視しながらハイパラを調整する

### 避けるべきこと

- 環境のテストを書かずにRL訓練を始める
- 固定相手での高勝率を汎化性能と混同する
- デフォルトハイパラのまま「動かない」と判断する
- 観測空間の次元を変えて旧モデルを流用する（再訓練が必要）
- 十分な初期方策なしにSelf-Playを試す

## まとめ

2週間でRL AIの勝率を0→100%まで持っていけた。ただしそれは7チームの固定相手に対しての結果で、32チームの多様な相手には71%（ヒューリスティクス）が現状のベスト。

RLの難しさはアルゴリズムの実装ではなく：
- **環境の正確性**。バグ1つで訓練結果が無駄になる
- **観測空間の設計**。情報が足りないと学習が進まない
- **対戦相手の多様性**。固定相手への過適合は汎化しない
- **分布シフトへの対応**。コンポーネント変更時の連鎖的再訓練

にある。これらを丁寧に設計すれば、PPOのような標準的なアルゴリズムでも十分な結果が得られる。
