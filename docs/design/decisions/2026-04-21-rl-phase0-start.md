# RL Phase 0 開始（2026-04-21）

## 背景と動機

4/17にヒューリスティックAIを大幅改善した。メガシンカ判定、Showdownデータ統合（902技・315特性）、特性考慮、速度推定、回復/壁判断、タイプベース選出を実装し、全マッチアップが100%決着するようになった。

この時点で**手動でのルール追加は収穫逓減**に入った。交代読み、確定数ベースの積み判断、相手の型推定などはゲームツリー探索や統計的推定が必要で、ヒューリスティクスの守備範囲を超える。

RLロードマップ（4/16策定）のPhase 0は「リプレイ模倣学習」。ここに進むことを決定。

## 1. fast_battle.py 分割リファクタリング

### 何をしたか

1,688行のfast_battle.pyを4つの専門モジュールに分割した。

### なぜ必要だったか

RL環境からAIのスコアリング関数やログパーサーを個別に呼ぶ必要があるが、fast_battle.pyが全部入りでは依存関係が不明確。また1,700行のファイルはAIエージェント（Claude）が正確に編集するのも困難になっていた。

### どう分割したか

Planningエージェントに全関数の依存グラフを分析させた結果、依存方向が一方向であることが判明:

```
log_parser.py → ai_scoring.py → ai_decision.py → fast_battle.py
                     ↑
                 showdown_data.py
```

サイクルが無いため、そのまま責務ベースで分割:

| ファイル | 行数 | 責務 |
|---------|------|------|
| `ai_scoring.py` | 396 | 技スコアリング、ステータス推定、マッチアップ評価 |
| `log_parser.py` | 323 | バトルログの全パース関数 |
| `ai_decision.py` | 675 | `_choose_action`本体、交代/メガ/選出判定 |
| `fast_battle.py` | 416 | Showdownプロセス管理 + リエクスポート |

`fast_battle.py`にリエクスポート（`from pokechamp.ai_scoring import ...`等）を配置することで、既存の244テストは変更なしで全PASS。

### 唯一の依存例外

`log_parser.py`の`_parse_opponent_from_log`が`ai_scoring.py`の`_estimate_opponent_speed`を呼ぶ。これは「ログパーサーがスコアリング層に依存する」逆方向の依存だが、ai_scoring → log_parserの方向は無いのでサイクルにはならない。

## 3. リプレイパーサー

### 何をしたか

リプレイログを(状態, 行動)ペアに変換するパーサーを作成した。

### パースで抽出する情報

各ターンの「プレイヤーが何をしたか」をサンプルとして抽出:

| フィールド | 内容 | 取得方法 |
|-----------|------|---------|
| `action_type` | move / mega_move / switch | `\|move\|`と`\|switch\|`行から |
| `action_detail` | 技名 or 交代先種族名 | 同上 |
| `active_species` | 場のポケモン | `\|switch\|`行の追跡 |
| `active_hp_pct` | 自分のHP% | `\|-damage\|`/`\|-heal\|`行 |
| `opp_active_species` | 相手のポケモン | 同上 |
| `opp_active_hp_pct` | 相手のHP% | 同上 |
| `team_preview_self/opp` | 6体のチーム構成 | `\|poke\|`行 |
| `weather` | 天候 | `\|-weather\|`行 |
| `winner` / `won` | 勝敗 | `\|win\|`行 |

### 選出情報の扱い — 重要な設計判断

リプレイログには選出の「宣言」が含まれない。`|switch|`行で場に出た時点で初めて判明する。そのため:

```
Turn 1: selected_known = ["Aegislash"]            ← 先発のみ
Turn 5: selected_known = ["Aegislash", "Hydreigon"]  ← 2体目が出た
Turn 9: selected_known = ["Aegislash", "Hydreigon", "Charizard"]  ← 3体目
```

**2つのフィールドを用意した:**

| フィールド | 内容 | 用途 |
|-----------|------|------|
| `selected_known` | その時点で判明している選出（不完全情報） | Phase 3.5: 不完全情報学習用 |
| `selected_full` | 同じリプレイの全ターンから遡って補完した完全選出 | Phase 0: 模倣学習用 |
| `opp_selected_full` | 相手の完全選出（同様に補完） | 同上 |

**なぜ2つ必要か:** 模倣学習では「上位プレイヤーが何を見て判断したか」を正確に教師信号にしたい。Turn 1の時点でプレイヤーは頭の中で3体を把握して行動している。`selected_full`はその内部情報を復元する。一方、将来のPhase 3.5では「序盤の不完全情報から選出を推定する能力」を訓練するため、`selected_known`も必要。

### 結果

| 指標 | 値 |
|------|-----|
| 入力 | 650リプレイ |
| 出力 | 13,600サンプル |
| 行動分布 | 技9,471 / メガ技913 / 交代3,216 |
| 3体選出完全データ率 | 84% |

## 4. 模倣学習 — Stage 1: attack/switch分類

### 何をしたか

「このターンは技を撃つべきか、交代すべきか」を予測する分類モデルを構築した。

### ラベル設計の試行錯誤

**最初の設計（3クラス）:** move / switch / mega_move

問題: `mega_move`はメガストーン持ちの初ターンのみの超レアラベル（7%）。モデルはmega_moveをほぼ予測できず（F1: 14%）。

**改善後（2クラス）:** attack（move+mega_move）/ switch

理由: メガシンカするかどうかは対面のタイプ相性で決まるルールベースの判断であり、ヒューリスティクスの`_should_mega_evolve`（既に実装済み）に任せるのが適切。模倣学習は「技を撃つか交代するか」という本質的な判断に集中すべき。

### 特徴量設計

| 特徴群 | 次元 | 内容 |
|--------|------|------|
| アクティブポケモン | 25 | タイプ(18) + 種族値(6) + HP%(1) |
| 相手アクティブ | 25 | 同上 |
| チームHP | 3 | 選出3体のHP% |
| 相手チームHP | 3 | 同上 |
| 天候 | 8 | one-hot |
| ターン数 | 1 | 正規化 |
| タイプ相性 | 2 | 攻撃/防御の最大倍率 |
| HP差・残数差 | 2 | 状況判断用 |
| **合計** | **69** | |

### データ量と精度の関係

| データ | サンプル数 | 精度 | Switch F1 | Macro F1 |
|--------|-----------|------|-----------|----------|
| 勝者のみ, 1300+ | 1,991 | 70.4% | 38% | — |
| 全員, 1200+ | 3,948 | 75.8% | 47% | 66% |
| 全員, 1200+（拡大） | **13,332** | **82.1%** | **59%** | **74%** |

**データ量が効く。** 3倍に増やすと+6ポイント改善。ベースライン（常にattackと答える）が68%なので、82%は有意な学習。

## 5. 模倣学習 — Stage 2: 具体的な技/交代先選択

### 何をしたか

「attackと判断した後にどの技を選ぶか」「switchと判断した後に誰に交代するか」を予測するスコアリングモデルを構築した。

### なぜ2段階か

リプレイには技のスロット番号（move 1〜4のどれか）が含まれない。技名（"Earthquake"）は分かるが、そのポケモンの4技の順序が不明。ポケモン個体の全4技が判明するのは全インスタンスの6%のみ。

→ Discrete(9)のenv.py互換出力は断念。代わりに**候補スコアリング**方式:
- 各候補（技 or 交代先）の特徴量を計算
- 「選ばれた候補」を正例、「選ばれなかった候補」を負例
- 2値分類で学習し、推論時はスコア最大の候補を選択

### ハードネガティブの重要性

Move scorerの最初の実装では、正例（実際に選んだ技）に対して**ランダムな偽特徴**をネガティブにした。結果は99.8%——簡単すぎて意味がない。

改善: 同じポケモンが同じリプレイ内で使った**他の技**をネガティブにした（ハードネガティブ）。精度は60%に落ちたが、これが現実的な難易度。

### Move scorerの特徴量（20次元）

基本特徴（8次元）:
- basePower, STAB, タイプ相性, カテゴリ, 優先度, 回復技, 積み技, 設置技

状況依存特徴（12次元）: ← これが精度改善に寄与
- **KO推定値**: 技威力×相性 / 相手HP → 止めを刺せるか
- **回復技の価値**: 回復×(1-自HP%) → HP低い時ほど価値UP
- **積み技の価値**: 積み×自HP%×(1-ターン/15) → HP満タン＆序盤ほど価値UP
- **設置技の価値**: 設置×相手残数/3 → 相手残り多いほど価値UP
- **先制技の価値**: 先制×(1-相手HP%) → 相手HP低い時ほど価値UP
- **ドレイン価値**: ドレイン率×(1-自HP%) → HP低い時の回復量
- **反動リスク**: 反動率×(1-自HP%) → HP低い時の自滅リスク
- **自己デバフ**: りゅうせいぐん等のC-2の重さ
- 自HP%, 相手HP%, 速度有利か, ターン数

### 精度の天井とその原因

| Stage | 3,948件 | 13,332件 | 伸び |
|-------|---------|---------|------|
| Stage 1 (attack/switch) | 75.8% | **82.1%** | +6.3 |
| Stage 2 Move | 44% | **45%** | +1 |
| Stage 2 Switch | 94% | **97%** | +3 |

**Move scorerの45%は構造的上限。** データを3.4倍にしても+1ptしか改善しない。

**原因:**

1. **「読み」の情報がリプレイにない。** 上位プレイヤーは「相手が交代する」と読んで技を選ぶ。同じGarchomp vs Corviknight対面でも、裏のHeatranを読めばEarth Power、居座り読みならScale Shot。特徴量にこの情報は入らない。

2. **同一状態に複数の正解がある。** ポケモン対戦は不完全情報ゲームで、最適戦略は確率的な混合戦略（技をランダムに混ぜる）。確定的な分類器では原理的に100%に到達できない。プレイヤーAが技A、プレイヤーBが技Bを選ぶ — どちらも「正解」。

3. **Switch scorerが97%と高い理由:** 交代先の選択はタイプ相性の差が大きく、「この対面にはCorviknightよりGarchompが明らかに良い」というケースが多い。技選択ほど微妙な判断が少ない。

**結論:** 模倣学習のMove scorerはこれ以上の改善にRL（自己対戦で試行錯誤）が必要。

## 6. FastBattleEnv — Gymnasium環境

### 何をしたか

Showdownサブプロセスを直接制御するGymnasium互換のRL環境を構築した。

### なぜ新しい環境が必要か

既存のenv.py（poke-env）はWebSocketでShowdownサーバーに接続する方式で、1戦15秒かかる。PPOの訓練には数万〜数十万エピソードが必要で、15秒/戦では実用的でない。

fast_battle.pyはShowdownをサブプロセスとして直接実行し、stdin/stdoutで通信する。1戦1秒。

### アーキテクチャ

```
FastBattleEnv(gym.Env)
  │
  ├─ env.reset()
  │   ├─ Showdownサブプロセス起動
  │   ├─ チームをpacked format変換して送信
  │   ├─ Team Preview: 両者ともヒューリスティクスで選出
  │   └─ p1の最初のrequestを取得 → 観測ベクトル化
  │
  ├─ env.step(action)
  │   ├─ p1のactionをShowdownコマンドに変換して送信
  │   ├─ p2はヒューリスティクスAI（_choose_action）が自動応答
  │   ├─ 次のp1 requestまで読み進む
  │   └─ 観測 + 報酬 + 終了判定を返す
  │
  └─ env.close()
      └─ サブプロセスを終了
```

**p1 = RLエージェント、p2 = ヒューリスティクスAI。** RLエージェントはヒューリスティクスAIに勝つことを学習する。

### 観測空間（93次元）

| 特徴群 | 次元 | 取得元 |
|--------|------|--------|
| アクティブ: タイプ | 18 | pokedex.json |
| アクティブ: ステータス | 6 | request JSON `stats` |
| アクティブ: HP% + 状態異常 | 2 | request JSON `condition` |
| 技4枠: 威力/相性/STAB/優先度/分類 | 20 | showdown_data + request JSON |
| 相手: タイプ | 18 | pokedex.json（ログからspecies取得） |
| 相手: HP% + 状態異常 | 2 | ログ `\|-damage\|` |
| チームHP(3体) | 3 | request JSON |
| 相手チームHP(3体) | 3 | ログ推定 |
| 天候 | 8 | ログ `\|-weather\|` |
| メガフラグ | 2 | request JSON / details |
| Force switch / Trapped | 2 | request JSON |
| アクションマスク | 9 | request JSON `moves` + `disabled` |

**showdown-request-spec.mdで文書化した仕様をそのまま実装。** request JSONに含まれない情報（basePower、types等）はshowdown_dataキャッシュから補完。4/17の「Contract-First Integration」の教訓が直接活きた。

### 行動空間

Discrete(9): move 1-4 + switch 1-5

メガシンカ: `canMegaEvo`が`true`かつ攻撃技の場合は自動的にmegaを付与（ルールベース判定）。

### 報酬設計

| イベント | 報酬 |
|---------|------|
| 勝利 | +1.0 |
| 敗北 | -1.0 |
| ターンごとのチームHP変化 | ±0.1 |
| 相手KO | +0.3 |

### 速度検証

```
Game 1: 4 steps, T4, winner=p2, 0.9s
Game 2: 19 steps, T16, winner=p2, 1.1s
Game 3: 14 steps, T12, winner=p2, 1.0s
Game 4: 9 steps, T7, winner=p2, 0.8s
Game 5: 13 steps, T11, winner=p2, 1.0s
Avg: 1.0s/game
```

ランダムエージェントはヒューリスティクスAIに全敗（当然）。1秒/戦で動作確認。

## 7. PPO訓練 — Phase 1開始

### 環境設定

stable-baselines3 (v2.8.0) + PyTorch (2.11.0) でPPOを実装。

FastBattleEnvの仕様:
- **観測**: 93次元（request JSON + ログパース + showdown_dataキャッシュ）
- **行動**: Discrete(9) — move 1-4, switch 1-5
- **報酬**: 勝利+1.0, 敗北-1.0, チームHP変化±0.1, 相手KO+0.3
- **速度**: ~1秒/戦、~2 FPS

### ハイパーパラメータの試行錯誤

**デフォルト設定（失敗）:**

```python
PPO(lr=3e-4, n_steps=64, ent_coef=0.01)
```

1000ステップ訓練→勝率0%。原因:
- `clip_fraction = 0`: 方策が全く更新されない
- `entropy_loss = -2.2`（一定）: 探索が発生していない
- 学習率が低すぎ、探索係数が低すぎ

**チューニング後（成功）:**

```python
PPO(lr=1e-3, n_steps=32, ent_coef=0.05)
```

| 変更 | 理由 |
|------|------|
| lr: 3e-4 → 1e-3 | 経験から速く学ぶ |
| n_steps: 64 → 32 | 短い経験で頻繁に学習 |
| ent_coef: 0.01 → 0.05 | もっと冒険的に行動を試す |

### 訓練結果の推移

| ステップ | 報酬(ep_rew) | entropy | 勝率 | 所要時間 |
|---------|-------------|---------|------|---------|
| 0 | -1.13 | 2.2 | ~0% | — |
| 1k | -0.63 | 1.1 | **70%** | 8分 |
| 2k | -0.04 | 1.3 | **75%** | +9分 |
| 3k | -0.26 | **0.6** | **20%** | +15分 |

### 過学習の発見（3kステップ）

2k→3kで勝率が75%→20%に急落。原因:

1. **Entropy崩壊**: 2.2→1.3→0.6。探索が減り、特定の行動パターンに固執
2. **固定マッチアップ**: p1=sand-mega-gyarados vs p2=mega-scizor-team の1通りだけ。この対面の最適解を暗記して汎化しなくなった
3. **報酬は改善**: -0.04→-0.26は「訓練中」の報酬。評価時に同じ相手なのに勝てないのは、訓練中のランダム性で偶然勝てていたが、deterministic評価で固定パターンが裏目に出た

### 対策: 対戦相手プールのランダム化

FastBattleEnvに`opponent_pool`パラメータを追加。reset()ごとにランダムな相手チームを選択:

```python
env = FastBattleEnv(
    team_paste=my_team,
    opponent_pool=[team_a, team_b, team_c, ...],  # 6チーム
)
```

これにより:
- 1チームへの過学習を防止
- 選出AIのヒューリスティクスも毎回違う相手で発動
- entropy崩壊を遅延（相手が変わるので同じ行動が通じない）

## 教訓

### 模倣学習の限界

1. **行動の種類の判断はデータで伸びる** — 82%まで到達。リプレイ追加でさらに改善可能
2. **具体的な技選択はデータで伸びない** — 不完全情報ゲームの混合戦略が原因。45%が天井
3. **交代先選択はタイプ相性で十分** — 97%。ヒューリスティクスと同等
4. **ハードネガティブが必須** — 偽特徴ネガティブは99.8%の幻想を生む

### Contract-First Integrationの効果

4/17に文書化した`showdown-request-spec.md`のおかげで、FastBattleEnvの観測空間設計でrequest JSONのフィールド欠如問題を事前に回避できた。

### PPO訓練の教訓

1. **ハイパーパラメータが全て** — デフォルト設定では1000ステップで勝率0%。lr×3, ent_coef×5で70%に到達
2. **固定マッチアップは過学習する** — 3kステップでentropy崩壊。対戦相手の多様性が必須
3. **チェックポイントを残す** — 2kが最良、3kは劣化。常にベストモデルを保持すべき
